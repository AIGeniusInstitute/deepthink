验收脚本自带数据准备（Phase A：注入 8 条反馈、触发采集与三层评价），不依赖外部前置数据，**可重复执行**：连跑多次不会因数据累积而改变判定（用例内断言均已按增量/幂等/时间戳口径写，见 §4.2）。

脚本自带**并发互斥锁**（`scripts/e2e/.flm-acceptance.lock`，`fs.openSync(..., 'wx')` 原子获取，持锁进程死亡可接管）：本套件会改全局配置（开关、采样率、脱敏规则、告警阈值），两个实例并发会互相污染并产出**互相矛盾**的证据，因此宁可拒绝并发。

## 4. 验收中发现并修复的缺陷（8 起）

这 8 起**全部在单元测试全绿、接口全部 200 的情况下存在**。它们的共同点是：单测覆盖的是后端纯函数产出，而缺陷长在**前端消费、上下游契约、事件循环、或"操作可重复性"**这四处单测够不到的地方。

| # | 缺陷 | 症状 | 根因类别 | Issue 文档 |
|---|---|---|---|---|
| 1 | 反馈去重把不同消息并成一条 | 多条不同反馈互相覆盖 | 去重键选错 | `2026-10-10-flm-feedback-dedup-collapses-distinct-messages.md` |
| 2 | 评价从不落库 | 「从评价中沉淀」永远 0 条 | `insertEvaluation` 零调用点 | `2026-10-10-flm-evaluations-never-persisted.md` |
| 3 | 工具调用失败信号全链路无人识别 | 三类归因分支线上从未触发 | 生产者/消费者状态取值集合交集为空 | `2026-10-10-flm-toolcall-failure-signal-never-detected.md` |
| 4 | 「学习沉淀」页签一行 `undefined.toFixed()` 打白整个控制台 | 点一次该页签，7 个页签全部不可用 | 前端 interface 声明了后端不存在的字段 | `2026-10-10-flm-learning-tab-crash-blanks-console.md` |
| 5 | 案例检索渲染三个不存在的字段 | 「相似度 NaN%」+ 标题空白 | 同上（检索接口与列表接口形状混用） | 同上 §2.1 |
| 6 | 案例库随每次沉淀膨胀，Top-K 返回重复候选 | Top-5 = 同一条案例的 5 份拷贝 | 派生数据缺幂等键 + 检索未去重 | `2026-10-10-flm-case-library-duplicates-and-topk.md` |
| 7 | `/admin/data-feedback` 同步计算 ~3.8s **冻结 Node 事件循环** | 该接口被调用期间，**同进程内所有其它 API**（含 192 字节的 `/health`）一起卡住 | 请求路径上的同步 CPU 密集计算 | `2026-10-10-flm-data-feedback-blocks-event-loop.md` |
| 8 | 加载失败被渲染成「暂无数据」 | 库里 53 个版本时页面显示「暂无策略版本」；失败痕迹 4 秒后随 toast 消失 | catch 只发 toast 不落 state + 空态文案是一次**事实断言** | `2026-10-10-flm-load-failure-rendered-as-empty-state.md` |

缺陷 7 是本轮最隐蔽的一起：它不产生任何错误，只是让**别的**接口变慢，因此最初表现为三个互不相关的用例（TC-17/18/28）超时。取证方式是并发探测 —— 在 `/admin/data-feedback` 执行 0.3s 后发一个 192 字节的 `/health`，实测耗时 3.46s；单独测 `search` 只要 13ms。修复（目标文本级记忆化）后：data-feedback 3.83s → 0.041s，健康探测 3.46s → 0.16s，且输出逐位不变。

缺陷 4/5/8 是同一族：**一个故障的表现形式与某种正常状态完全同形**。缺陷 4 表现为"页面白屏"（明显），缺陷 5 表现为"相似度 NaN%"（也明显），而缺陷 8 表现为**一句自信的"暂无数据"** —— 最危险，因为它把偶发故障永久升级成了错误结论。

缺陷 8 原先也在这一列 —— 它的触发是**瞬时且不可复现**的（服务端无请求记录，重放 10 次均成功），所以"修好之后跑一遍通过"根本不能证明修复有效：通过只是因为这次没失败。为把它从"无法证伪的声明"变成"可判定的证据"，新增了 **TC-33**：用 Playwright `page.route` 主动 abort 掉列表接口，把那次不确定的失败**变成确定事件**，从而可以稳定地断言"失败必须显式可见、且不得伪装成暂无数据"。这是本轮唯一一条**为验证修复而新增**的用例。

### 4.2 本次验收对"判据本身"的加固（10 处）

审查验收脚本时发现 10 处判据失效。**它们全部会让脚本"看起来更绿"**，因此比产品缺陷更危险：

| 用例 | 原判据为什么是假的 | 加固方式 |
|---|---|---|
| TC-06 | 要求"点击后新增系统事件"，但 Phase A 已把种子任务全部采完，去重后**必然为 0** —— 断言恒假 | 改为验证**按钮接线**：POST 端点、`taskId` 与输入框一致、返回值为数值、toast 回显。与去重无关 |
| TC-10 | 读 `?limit=200` 最新 200 条，要求 user/env/system 三类齐备。表增长后窗口被 user 占满（实测 user=192/env=14/system=8，而窗口 200 = 186+14），system 被**挤出窗口** | 改为**按来源分查**（端点支持 `?source=`），不受"最新 N 条"影响 |
| TC-25 | 判据是 `/generate\|gate\|canary\|rollback\|audit/` —— 一个**或**：任一条 gate 记录就能让"全链路可回放"通过，与用例要证的东西恰好相反 | 四个动作**分别**必须出现，并列出缺失项 |
| TC-29 | 两侧指标取自同一组 `GOOD_GATE`，六项全「持平」（0 差值）—— 表格、判定列、建议列都在渲染，却没有任何**判别** | 现场用 `BAD_GATE` 造出真实劣化，断言出现「劣化」判定且建议转为「不建议放量」 |
| TC-30 | 用告警**总条数**增大判"产生了新告警"，被 `limit` 截断后饱和（112→114 之后恒等） | 改判**最新告警时间戳**是否推进 |
| TC-31 | 用 `events?limit=500` 前后条数相等判"不再新增"，表涨过 500 行后**恒真** | 改按 `created_at ≥ 本次动作时刻` 取证 |
| TC-32 | `degraded !== true` 对 `undefined` 也为真 —— 请求彻底失败也算"恢复成功" | 要求正证据：`degraded === false` **且** `eventInserted === true` |
| TC-21 / TC-24 | "直接放量被拒""人工签字成功"只写在 `details` 里，判据从未使用 —— 计算了但没断言（dead discriminator） | 收进 `passed` |
| TC-23 / TC-24 | 列表为空有两种含义（库里真没有 / 这一次没拉到），但失败表现为 `page.click: Timeout 20000ms`，把排查引向"选择器写错了" | 新增 `waitStrategiesList()`，未加载则显式失败并回显页面自述原因 |
| TC-33 | （新增）缺陷 8 的失败不可复现 → 修复无法被证伪 | route 拦截制造确定失败 |

**仍未加固的项（如实列出）**：TC-04、TC-05、TC-08、TC-11、TC-16、TC-19、TC-26、TC-28 的判据仍以"元素存在 + 文本包含"为主，属**存在性断言**而非取值断言。它们能证明"界面渲染了这块内容"，**不能证明内容正确**。本轮未改，因为这几条对应的正确性已由单元测试在值层面覆盖（253 条），UI 层只需确认可达性。

### 5.1 AC-F4.4 的实测说明

PRD 要求「案例检索 Top5 命中率 ≥ 80%（用标注命中集合实测）」。实测方式：构造 8 条标注案例（目标 + 轻改写查询），逐条检查其目标是否出现在 Top-5，实测命中率 **8/8 = 100%**，断言 `≥ 0.8`（`tests/units/flm-learn.test.ts`）。

**这条 AC 曾经是不可度量的**：修复缺陷 6 之前，Top-5 会被同一条案例的 5 份拷贝占满，"5 个槽位里有几个是有效候选"在语义上不成立。Top-K 去重之后该指标才真正可测 —— 这也是把候选互异性写进 TC-17 判据的原因。
