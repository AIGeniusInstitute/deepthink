## 2. 向量模型：确实生效（硬证据是检索，不是配置页）

配置项显示"已启用"**不能算数** —— 配置写没写进库、向量有没有真的算出来、
检索臂有没有真的用上，是三件不同的事。所以直接问检索：

```
POST /api/paas/knowledge-bases/<id>/search
{"query":"录错了受试者的信息要怎么修正？","top_k":3,"mode":...}
```

| 模式 | 命中 | 得分 |
|---|---|---|
| `keyword` | **0** | — |
| `vector` | **3** | 0.6754 / 0.6440 / 0.6257 |
| `hybrid` | 3 | 0.0115 / 0.0113 / 0.0111 |

**关键词臂 0 命中、向量臂 3 命中** —— 这条中文整句能不能被检索到，
**完全取决于向量臂**。命中卡片上的分项也印证了这点：`向量分: 0.6333  关键词分: 0.0000`。

这正是 PRD 里根因 B 被修掉的直接证据：配向量模型之前，这条查询在 9999 上是 0 命中。

配置本体：`bge-m3`，1024 维，走本机 Ollama `http://127.0.0.1:11434`，
经界面「设置 → 本机模型服务 → 一键启用」写入（`{"success":true,"model":"bge-m3","dimensions":1024}`）。
**没有申请任何外部 API Key。**

## 3. 落地时发现的新缺陷：「重建索引」后列表仍显示「已向量化 0」

### 3.1 现象（修复前，截图 `30-9999-before-rebuild.png`）

```
eCRF填写指南-信达生物-CIBI3026A101_CCI_V1.0_20260106.pdf
201.1 KB · 分块 266 · 已向量化 0 · 2026-10-16T10:02:29.258Z
```

同一时刻查库：

```
kb_documents.embedded_chunk_count  → 0
kb_chunks  COUNT(*)|COUNT(embedding) → 267|267
```

**数据是对的，界面在撒谎。** 检索也确实能命中（§2），所以这个 0 是纯粹的显示错误 ——
但它会实打实地把用户推向"重建索引没生效、我再点一次"的错误动作。

### 3.2 根因

`kb_documents.embedded_chunk_count` 是**冗余计数列**，只由 ingest 管线维护。
`POST /:id/rebuild-index` 直接调 `embedAllChunksInKb()` 批量补向量，**绕开了那条管线**，
于是没人更新计数列。而 `rebuild-index` 恰恰是用户为了"把向量补上"才会点的按钮 ——
这条路径上的用户 100% 会看到那个错误的 0。

### 3.3 修复与复核（截图 `32-9999-after-rebuild.png`）

修复见 `docs/issues/2026-10-16-kb-embedded-count-stale.md`

同一台 9999、同一个知识库、同一份文档，点一次「重建索引」之后：

| | 重建前 | 重建后 |
|---|---|---|
| 分块 | 266 | 266 |
| **已向量化** | **0** | **266** |
| toast | — | `索引重建完成：重新分块 0 个文档，向量化 0/0` |

请对照 `30-9999-before-rebuild.png` 与 `32-9999-after-rebuild.png` —— 是同一页面的前后两帧。

> toast 里那句「向量化 0/0」是**对的但容易误读**：本轮确实没有待嵌入的分块（266 个早就嵌好了），
> 「0/0」指的是**这一批**，不是全库。列表上的 266 才是全库真相。
> 这个措辞落差已如实记进 issue 文档的 §8.3，本轮不改。

### 3.4 回归用例锁住这个缺陷

`tests/units/kb-rebuild-index-count.test.ts`（3 项）。断言点**刻意选在列表接口**而不是接口返回的
`attempted/success` —— 因为这个缺陷的表现就是"接口返回全对、列表全错"，只断言 stats 是抓不到的。

把修复回退后跑，失败在预期的那一行：

```
AssertionError: expected +0 to be 1
 ❯ tests/units/kb-rebuild-index-count.test.ts:162
     expect(doc.embedded_chunk_count).toBe(doc.chunk_count);
```

## 4. 顺带复核：用户 16:18 报的「上传文档点了没反应」

该缺陷在 `48ef60a` 已修（根因：`<label>` 包裹 `<button>`，规范要求 label 对
interactive content 后代的点击「什么都不做」，于是点击被吞掉）。

在 9999 上按**真实点击路径**复核 —— 点按钮、等 `filechooser` 事件，而不是绕过去给 input 赋值
（那条路按钮坏了也照样"通过"）：

```
✅ 点「上传文档」弹出文件选择框（真实点击路径）
```

截图：`31-9999-upload-button.png`。为不往生产库里塞测试文件，探针在文件框弹出后即取消。
