## 4. 工作原则【最高宪法】（原文）

1. **Think Before Coding** —— 不要假设、不要隐藏困惑、主动暴露取舍。非平凡改动前显式声明假设；存在多种合理解释时全部列出；不清楚就停下发问。
2. **Simplicity First** —— 最小可用代码，不做投机性设计。禁止未被要求的功能、单次使用的抽象、不必要的可配置性、对不可能发生场景的错误处理。自检问句：「有经验的工程师会认为这过度设计了吗？」
3. **Surgical Changes** —— 只碰必须碰的。不「顺手优化」周边代码、不重排没弄坏的东西、不重构自己不认同的模式。区分「自己引入的死代码」（清理）与「既有死代码」（指出但不碰）。
4. **Goal-Driven Execution** —— 定义成功标准，循环直到验证通过。把任务转成可度量目标 + 显式验证步骤。

## 5. FLM 模块需求（用户提供的 PRD V1.0 全文要点）

> 用户随任务一并提供了「AI Agent 平台 · 反馈与学习自进化模块 PRD V1.0」全文。
> 完整原文见 `docs/prd/feedback-learning-module/PRD.md` 的「附：用户原始 PRD」章节；此处保留其结构与硬性口径，作为不可裁剪的需求基线。

### 5.1 模块定位

位于「行动执行」之后、「再规划」之前的能力中枢，负责把一次任务的真实结果转化为可复用的改进策略。
模块代号 **FLM**（Feedback & Learning Module）。

### 5.2 背景与现状问题（原文 P1–P5）

| 编号 | 问题 | 影响 |
|---|---|---|
| P1 | 反馈采集分散（会话界面 / 工单 / 问卷 / APM / 业务系统） | 无法形成完整证据链，复盘靠人工拼凑 |
| P2 | 反馈未被结构化（显式反馈多为非结构化文本） | 反馈「看得见、用不上」 |
| P3 | 评价维度单一（仅以「是否报错」为准） | 大量「无报错但不达标」任务被误判为成功 |
| P4 | 经验无法沉淀（成功与失败轨迹未保存） | 同类问题反复发生，重复消耗算力与人力 |
| P5 | 缺少闭环（分析结果不回写策略） | 只观测、不进化，指标长期停滞 |

### 5.3 建设目标（原文 1.3）

- 建立覆盖**用户反馈、系统日志、环境数据**三类来源的统一反馈采集能力。
- 建立统一分析框架，将多源异构反馈映射到一致的评价维度。
- 建立**结果层、过程层、质量层**的三层评价分析引擎，并支持失败归因到具体环节。
- 建立学习自进化链路：**短期纠偏、中期经验沉淀、长期策略优化与模型对齐**。
- 建立闭环执行与**灰度回滚**机制，保证进化过程安全、可控、可追溯。

### 5.4 非目标（原文 1.4）

- 不自建通用大模型训练基础设施，仅产出训练与对齐数据集，通过接口对接现有训练平台。
- 不替代现有 APM / 日志平台，只做订阅、采样与二次结构化。
- 不改造业务系统内部流程，仅通过开放接口读取环境状态与流程流转结果。

### 5.5 成功指标（原文 1.5）

| 指标 | 基线 | 目标（上线后 3 个月） |
|---|---|---|
| 任务成功率 | 待埋点补齐 | 提升 8 个百分点 |
| 用户显式满意度 | 待埋点补齐 | ≥ 85% |
| 失败归因覆盖率 | < 30% | ≥ 90% |
| 同类问题复发率 | 无统计 | 下降 40% |
| 自动纠偏成功率 | 无能力 | ≥ 60% |
| 反馈闭环时延 | 无闭环 | ≤ 24 小时 |

### 5.6 功能需求（原文第 5 章，F1–F6）

**F1 反馈采集层**
- F1.1 用户反馈采集：显式（点赞/点踩、1–5 分评分、采纳/否决、纠错文本、补充要求、重新生成、中途终止）；隐式（重复提问、指令改写、会话静默放弃、结果复制率、结果修改幅度、二次确认通过率）；点踩原因标签（答非所问/事实错误/格式不符/过于冗长/未完成任务/其他）；上下文绑定 task_id/step_id/trace_id 并快照输入输出；Web/移动端组件 + 服务端 API 两种入口。
  - 验收：反馈产生到可查询 ≤ 5 秒；反馈与轨迹绑定成功率 ≥ 99.9%；单条反馈提交不阻塞主链路。
- F1.2 系统日志采集：范围含工具调用回执、错误码、耗时、重试次数、返回字段完整性、LLM 调用日志、Token 消耗、链路 Trace、限流超时；支持消息队列订阅与日志文件采集，兼容 OpenTelemetry；默认全量、可按智能体/租户配采样率与字段白名单；进归一化层前完成字段抽取与类型标准化。
  - 验收：支持亿级日写入；端到端可见时延 ≤ 5 秒；字段抽取成功率 ≥ 99%。
- F1.3 环境数据采集：任务前后环境状态快照 diff、业务流程流转节点、外部系统状态变更、上下文更新；全量快照 + 增量订阅；业务侧可自助注册关键状态字段为观测点；带时间戳与有效期，过期数据不参与判定。
  - 验收：支持自助注册观测点；快照 diff 计算时延 ≤ 30 秒；跨系统时钟偏移可校准。
- F1.4 三类反馈来源对照表（用户反馈 / 系统日志 / 环境数据）。

**F2 统一分析框架（归一化层）**
- F2.1 统一事件模型 FeedbackEvent 标准 Schema（字段见第 6 章）。
- F2.2 实体对齐：task_id / trace_id / session_id / step_id 四级主键跨来源关联，缺失时基于时间与内容兜底。
- F2.3 时序对齐：统一时间基准、重建反馈时间线、支持乱序修正。
- F2.4 冲突消解与置信度：用户主观反馈与系统客观日志冲突时按来源权重与置信度加权；异常值与刷量噪声过滤。
- F2.5 去重：同来源重复事件按时间窗去重。
- F2.6 脱敏：归一化阶段完成敏感信息识别与脱敏，脱敏后方可进入分析与学习链路。
- 验收：跨来源实体对齐准确率 ≥ 95%；冲突消解策略可配置；脱敏覆盖手机号/身份证/银行卡/邮箱/Token 且可热更新。

**F3 三层评价分析引擎**
- F3.1 结果层：判定「达成 / 部分达成 / 未达成」三档；LLM-as-Judge 与规则判定双轨，不一致进人工复核队列。
- F3.2 过程层：比对实际路径与预期规划路径算路径符合度；统计步骤耗时与重试次数识别瓶颈；定位首个异常步骤。
- F3.3 质量层：事实性、格式合规、响应时延、成本消耗、安全合规、用户偏好匹配六维评分。
- F3.4 归因分析：未达成与质量不达标任务定位到意图理解 / 规划 / 工具选择 / 参数生成 / 执行 / 总结。
- F3.5 评价可解释：每个结论附带证据片段（反馈原文、日志行、环境 diff），支持人工复核。
- 验收：归因结论带证据、可解释率 100%；结果层判定与人工抽检一致率 ≥ 90%；单任务评价耗时 ≤ 10 秒。

**F4 学习与自进化层**
- 三层时效：短期（会话内秒级，重试/重规划/切换工具/改写参数）、中期（跨会话天级，经验记忆库沉淀成功与失败轨迹、相似任务检索复用）、长期（跨版本周级，策略版本迭代、工具路由与参数模板优化、训练数据集回流）。
- F4.1 短期纠偏：可配置重试策略（次数上限、退避规则、切换工具白名单），超限终止并降级人工。
- F4.2 经验记忆：任务目标与上下文向量化索引、相似案例检索；成功轨迹正样本、失败轨迹负样本分别入库。
- F4.3 策略优化：Prompt 模板、工具路由规则、参数模板、Few-shot 样例库的版本化管理与自动更新建议。
- F4.4 数据回流：自动产出偏好对比数据（chosen/rejected）、SFT 语料、评测集扩充样本，交付训练平台。
- F4.5 知识库自更新：纠错类反馈沉淀为知识条目候选，审核后写入业务知识库。
- 验收：短期纠偏不得导致任务耗时超过原任务 2 倍；案例检索 Top5 命中率 ≥ 80%；自动产出训练数据必须标注来源与生成时间、可追溯。

**F5 闭环执行与安全机制**
- F5.1 策略版本管理：所有策略变更生成新版本，记录变更内容、触发来源（自动/人工）、关联归因标签。
- F5.2 回归评测门禁：新版本上线前必须通过回归评测集，任一核心指标劣化超阈值即拦截。
- F5.3 灰度发布：按租户/智能体/流量比例灰度，最小流量 1%。
- F5.4 自动回滚：灰度期核心指标劣化超阈值或错误率突增，自动回滚上一稳定版本并告警。
- F5.5 人工审核：涉及安全合规、对外承诺、资金相关的策略变更强制人工审核。
- F5.6 全链路审计：策略每次生成、发布、回滚均留痕，支持按时间线回放。
- 验收：回滚触发到生效 ≤ 60 秒；评测门禁拦截准确率 100%；审计日志保留 ≥ 180 天。

**F6 运营观测控制台**
- F6.1 反馈总览看板：反馈量、满意度、成功率、纠偏率、反馈闭环时延等核心指标趋势。
- F6.2 归因分析视图：按归因环节、错误码、工具、智能体、租户多维下钻。
- F6.3 案例检索与标注：按条件检索任务轨迹与评价详情，人工修正归因标签并回流训练。
- F6.4 策略版本对比：任意两版本 A/B 指标对比，输出是否放量建议。
- F6.5 告警：指标突降、错误率突增、反馈量异常可配阈值告警，推送企业 IM。
- 验收：看板数据延迟 ≤ 5 分钟；支持下钻到单条任务轨迹；人工标注结果 24 小时内回流学习链路。

### 5.7 核心数据模型（原文第 6 章）
