01系统定位与全貌

DeepThink 是一个可自托管的、多租户的 Agent 基础设施。它把「人类-程序员协作」与「Agent 自主执行」放在同一个运行时里：每个用户拥有一个主容器（is_home），每个会话是一个独立的文件系统与 IPC 命名空间，所有编排能力收敛到一个 DAG 引擎上。

AI 自主研发平台
Agent 独立完成软件研发全生命周期，容器内挂载工作区、Skills、MCP 工具与沙箱浏览器。
自进化引擎
src/autonomy/ 事件总线 + 能力注册 + 学习与教训注入 + 自愈适配，从错误中沉淀。
程序员-Agent 协作中枢
个人「开发项目」内含多个并行会话，中央 group-queue 调度防止并发冲突。
企业级 SaaS
多租户隔离、RBAC 六权限、计费配额、IM 企业集成（飞书 / 钉钉 / 企微生态）。
超级智能体孵化器
Team Builder、Orchestrator-Workers、Swarm 群组、Loop Engineering 四类协作范式。
全栈可观测
trace_steps / trace_span 双层 trace、Eval Center 漂移检测、Harness 评估断言。
阅读这份文档的方式

如果你要改代码，先读 §03 三个横切面——绝大多数改动都会碰到它们，而它们光看目录结构看不出来。如果你要找某个 API，从 src/web.ts（路由挂载点）反查，不要只翻文档。

02分层架构图

自上而下七层。关注点分离的关键在于：接入层与业务域层对执行引擎无感知——所有引擎适配器产出同一套 StreamEvent，上层管道只认事件不认引擎。

层的职责边界

层职责关键约束
① 接入层七种 IM 通道 + Web/桌面/移动三种终端形态 + 开放平台 API只与网关层对话，不直接触达引擎
② 网关层路由挂载、认证、RBAC、WS 升级与广播路由挂载点是 src/web.ts，单一真相源
③ 业务域层45 个路由模块 + 13 个业务子系统目录（src/ 下 14 个子目录除去 routes/），每个业务面一个 store不自行实现编排，复用图谱引擎
④ 核心引擎层图谱编排、多引擎执行、自主进化、意图拦截新增编排能力优先扩图谱引擎，不另起链路
⑤ 运行时层并发调度、容器/进程生命周期、SDK 会话循环、定时触发不丢消息、不重复回复、失败可重试
⑥ 状态层持久化、跨 Pod 协调、对象存储、向量检索默认单机开箱即用，设环境变量即切分布式
⑦ 外部依赖Claude Agent SDK（内置 CLI 运行时）、LLM Provider、S3SDK 与 CLI 始终取最新版本

03三个横切面

下面三层不属于任何单个模块，但几乎所有改动都会碰到，而且光看目录结构看不出来。 改动执行或状态之前，先读这一节。

① 多 Agent 执行引擎 —— RegisteredGroup.engine

决定这个群组用哪个引擎跑 Agent，共 5 个。类型定义在 src/types.ts 的 AgentEngine。

engine运行时adapter
claude 默认Claude Agent SDK（内置完整 Claude Code CLI 运行时）index.ts 的 SDK 分支（内联在容器入口内）
atomcodeAtomCode 自带 HTTP/SSE daemonatomcode-engine.ts + src/atomcode-daemon-manager.ts

opencodeOpenCodeopencode-engine.ts
pipi（stdio JSONL RPC）pi-engine.ts
为什么新增引擎只需要写一个 adapter

分发是懒加载动态 import：agent-runner 读 ContainerInput.engine，非 claude 时 branch 到对应 *-engine.ts， 各 adapter 产出同一套 StreamEvent。所以上层（容器管理、流式管道、WebSocket 广播）对引擎完全无感知——新增引擎只写 adapter，不要改上层管道。 容器内每个引擎的 CLI 与凭据注入在 src/container-runner.ts。配置入口是 /engines 页面 + 设置页对应 tab。

② 图谱引擎 —— src/graph-engineering/

平台唯一的 DAG 编排内核（12 个文件），被多个业务面复用：Team Builder、Agent Workflow 可视化编排、Orchestrator-Workers、Agent 群组（Swarm）、Loop Engineering、Harness Eval。

新增编排能力优先扩这个引擎。v1.4.0 的 Swarm 曾另起一套 Redis 链路，结果从未跑通 （故障复盘）； v1.5.0 的修复就是把它删掉、改回这个引擎，并通过 GraphDeps 的 onNodeSettled / onNodeStream 两个加性、未接线即 no-op 的回调注入 Swarm 语义。

③ 可插拔状态层

默认单机开箱即用；设了环境变量即切到分布式，代码路径不变。

关注点默认切换开关实现要点
数据库SQLite（WAL）
better-sqlite3		 DATABASE_URL=postgresql://… src/sqlite-compat.ts 是唯一的后端选择点；src/pg-sync-driver.ts 用 worker_threads + Atomics.wait 把异步 pg 同步桥接回 better-sqlite3 的同步 API（db.ts 有 400+ 同步调用点，这是根本原因）；SQL 方言由 src/sql-translator.ts 运行时翻译
跨 Pod 协调进程内 REDIS_URL src/redis-bus.ts 是唯一且完整的实现（28 个导出：WS 广播 pub/sub、分布式锁与选主、Agent IPC、共享并发计数器、turnMounts 跨 Pod 传递）。未配置时全部降级为 no-op / in-memory
大文件 / trace IO本地文件系统 OBJECT_STORE_PROVIDER=s3 src/object-store.ts；output_ref 统一为绝对路径或 s3://bucket/key，读写两端必须走同一处保持对称
向量检索sqlite-vec（vec0 虚表） PostgreSQL → pgvector src/embedding.ts；两者都加载失败时回落线性扫描，未配置 embedding 时回落 FTS5
IM 长连接归属本进程独占 Redis 选主 多 Pod 下只有一个 Pod 接管 IM 长连接：deepthink:im-leader 租约（30s TTL，续约失败即让位），见 src/index.ts。同一套租约原语（acquireOwnership / renewOwnership）也用于调度器单写者
改 db.ts 或任何持久化路径时的硬约束

必须同时保证 SQLite 与 PostgreSQL 两种后端可用。PG 模式禁用 SQLite 专有语法——ADD COLUMN IF NOT EXISTS 的语义差异曾导致迁移中断。 另一个已记录在案的坑：PG 模式下 translateCreateTable 会剥掉外键约束（PG 在解析期就要求目标表存在）， 所以同一套 DDL 里的外键只在 SQLite 上真正生效，且启动时有 PRAGMA foreign_keys 守卫会在检测到孤儿行时直接关闭强制。

执行模式

模式行为适用对象
hostAgent 作为宿主机进程运行，通过 claude CLI 直接访问宿主机文件系统admin 主容器（folder=main）
containerAgent 在 Docker 容器中运行，通过卷挂载访问文件，完全隔离member 主容器（folder=home-{userId}）及 Docker 可用时的其他群组
执行模式不是按 is_home 静态推导的

除 loadState() 那条规则外，还有两条路径会产出 host：

  1. 新建非主工作区时按 Docker 可用性降级：executionMode: (await isDockerAvailable()) ? 'container' : 'host'。Docker 不可用时新建的 flow 工作区直接跑在宿主机上。
  2. schedule_task 继承来源模式：未显式指定时 executionMode = sourceIsHost ? 'host' : 'container'；显式请求 host 但来源是容器时会被强制回 container。

所以「非主工作区 = container」是常见情形而非保证。判断某个群组实际用什么模式，查 registered_groups 表里该行的值，不要从 is_home 推。

06领域模型与 ER 图

建表语句有两处，改 schema 时别漏：src/db.ts（90 个表名）与 src/eval-center/eval-schema.sql（评测中心独立的 16 张表），合计 106。权威版本号是 src/db.ts 的 SCHEMA_VERSION——当前 '70'，改动前先读那里，不要相信任何文档里的版本数字。

三个必须知道的 schema 事实
  • 外键在 PostgreSQL 上被剥离。translateCreateTable 会移除 FK 约束（PG 在解析期就要求目标表存在）。 所以本文所有「外键」关系只在 SQLite 上真正强制；且启动时有 PRAGMA foreign_keys 守卫，检测到孤儿行会直接关闭强制。
  • registered_groups.folder 按设计不唯一——多个飞书群组可映射到同一 folder，旧的 UNIQUE 约束已由迁移移除。 所以 folder → *.group_folder 是 1—N。
  • 约 20 个列不在基础 DDL 里，而是由 ensureColumn / ALTER TABLE 追加 （agent_def_id、graph_definition_id、floor_policy、group_kind、八个 sessions.*_session_id 等）。 只按基础 DDL 生成的 ER 会漏掉 6 条关系和一批列。

8.3 两种执行模式

host — 宿主机进程
node container/agent-runner/dist/index.js 直接作为宿主机进程运行，通过 SDK 访问宿主机文件系统。 并发上限 MAX_CONCURRENT_HOST_PROCESSES（默认 5），支持 customCwd。
用于 admin 主容器（folder=main）。
container — Docker 隔离
镜像 deepthink-agent:latest，基于 node:22-slim + Chromium，以 node 非 root 用户运行。 并发上限 MAX_CONCURRENT_CONTAINERS（默认 20）。
⚠️ 执行模式不可从 is_home 静态推导
除了 loadState() 那条「admin 主容器 = host」的规则外，还有两条路径会产出 host：
  1. 新建非主工作区时按 Docker 可用性降级：executionMode: (await isDockerAvailable()) ? 'container' : 'host'（src/index.ts:2104）。Docker 没启动 → 新工作区直接跑在宿主机上。
  2. schedule_task 继承来源模式：未显式指定时 executionMode = sourceIsHost ? 'host' : 'container'；显式请求 host 但来源是容器时会被强制回 container（src/index.ts:6648-6663）。
所以「非主工作区 = container」是常见情形而非保证。判断某个群组实际用什么模式，查 registered_groups 表里该行的值。

9.2 图谱引擎的加性扩展点（GraphDeps）

这是平台推荐的唯一一种给图谱引擎加能力的姿势：加一个可选回调，未接线即 no-op，对既有 graph run 零影响。

回调必需用途
registeredGroups()必需群组快照，用于解析执行模式
getSessions()必需会话 ID 映射
onProcess(...)必需把子进程登记进容器管理（终止 / 超时 / 终端）
broadcastStreamEvent?可选节点流事件广播到 Web
storeResultAndNotify?可选落库 + 多渠道通知
storeApprovalCard?可选Human-in-the-loop：暂停运行并推送审批卡片
onNodeSettled?可选节点终态回调。收到完整的 NodeRunOutcome（而非被截到 500 字符的 graph_node_end），所以席位回复能原样落库
onNodeStream?可选事件广播前的钩子。Swarm 用它把席位的裸 text_delta 翻译成带座位号的 group_message_delta

onNodeSettled / onNodeStream 是 v1.5.0 为 Swarm 加的加性钩子，注释里明确写了 "Optional — no-op for every existing graph run"。
