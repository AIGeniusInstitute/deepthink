# PRD · 本机内置模型服务 + 扫描件 OCR

- **日期**：2026-10-16
- **来源需求（原文）**：「扫描件要支持，9999 那个实例要配向量模型，直接系统内置部署使用开源的向量模型服务。」
- **前序**：`docs/issues/2026-10-16-kb-pdf-parse-crash-and-fabricated-page-markers.md`（D7/D8）
- **状态**：已实现，待验收

---

## 1. 背景

### 1.1 用户侧的现象

1. 用户在 9999 实例上传《CSCO 非小细胞肺癌治疗指南 2026》（287 页扫描件），上传成功但知识库检索不到任何内容。
2. 知识库的「已向量化」始终是 0 —— 9999 从未配置过 Embedding。

### 1.2 根因（两条独立的问题）

| # | 问题 | 证据 |
|---|---|---|
| A | 该 PDF 是**纯图片扫描件**，没有文字层。`pdf-parse` 抽出的 `result.text` 是 574 个纯换行，trim 后为空，被空值守卫拦下并报错。**当时的正确行为，但不是用户要的结果** —— 用户要的是"能检索到"。 | `docs/issues/...-pdf-parse-crash...md` §3 |
| B | 9999 的 `data/config/embedding.json` 不存在，`getEmbeddingConfig()` 返回 null，向量臂整体跳过，只跑 FTS5 关键词检索。而关键词臂是 trigram 子串语义，中文整句不命中。 | `~/.deepthink-9999/config/` 无 embedding.json；`kb_chunks` 中 `embedding IS NOT NULL` 计数为 0 |

### 1.3 为什么这两件事要一起做

只做 A：OCR 出来的正文仍然只能走关键词臂，中文长句检索不到 —— 用户还是"看不到结果"。
只做 B：向量检索建好了，但扫描件进不了库 —— 向量臂没有东西可检索。
**两个需求合起来才构成「扫描件也能被检索到」这一个可交付结果。**

## 2. 目标与非目标

### 2.1 目标

| # | 目标 | 验收标准 |
|---|---|---|
| G1 | 无文字层的 PDF 上传后能被 OCR 并入库 | 上传扫描件 → 文档状态经过 `OCR 识别中` → `就绪`，`分块 > 0` |
| G2 | OCR 结果保留表格的行列结构 | 扫描页中的表格在分块正文里呈现为 Markdown 表格，行列不串 |
| G3 | 管理员不需要任何 API Key 就能开启向量检索 | 在设置页点一次「一键启用」→ 无需填写 baseUrl / apiKey |
| G4 | 9999 实例完成落地 | 9999 的 `已向量化 > 0`，且一次真实检索能命中 |
| G5 | OCR 是分钟级操作，不能阻塞上传请求 | 上传接口在 1 秒内返回 201，进度通过列表轮询可见 |
| G6 | 单页 OCR 失败不毁掉整本文档 | 287 页中失败 2 页，其余 285 页正常入库，失败页码在正文中留痕 |

### 2.2 非目标（明确不做）

- **不做**在 Node 进程内跑推理（onnxruntime / transformers.js）。理由见 §3.2。
- **不做**跨页表格合并、公式识别、手写体识别。
- **不做** OCR 结果的人工校对界面。
- **不做**视频/音频的转写。
- **不动**知识库复刻的 P2–P5 计划（本次只解决扫描件与向量模型两个具体缺口）。
- **不使用** `~/Downloads/配对数据集_原文与金标准/` 里的临床数据做测试 —— 该数据集标注为保密且"别外发、别上传第三方服务"。

## 3. 关键决策与取舍

### 3.1 OCR 引擎：视觉大模型 vs 传统 OCR（tesseract / PaddleOCR）

**选视觉模型（默认 `qwen3-vl:8b`）。**

理由是从真实样本出发的，不是偏好：

- 实际要处理的扫描页（用户那份指南的第 1、2、40 页）是**表格密集**页 —— 第 40 页整页是一张「ALK 融合阳性非小细胞肺癌的治疗」推荐表。
- 传统 OCR 的输出是**按行拼接的散字**，表格的行列关系丢失。一行里的三个单元格会被拼成一句话，检索时语义错乱；并且没有可用的行/列分隔符，下游无法还原。
- 视觉模型可以直接按 Markdown 表格输出，行列结构完整保留在文本里。

代价：慢（8B 模型单页数秒到数十秒），且需要下载 6GB 权重。这是**用处理时长换检索质量**的取舍，在"文档进库是一次性的、检索是长期的"这个场景下方向正确。

### 3.2 模型服务：复用本机 Ollama vs 把推理引擎编进 Node 进程

**选复用本机 Ollama。**

- 「系统内置」的诉求是**管理员不需要去申请 API Key**，不是"不能有独立进程"。
- 把推理引擎编进进程的两条路都不可行：`onnxruntime-node` 要么绑定特定模型、要么把 1GB 权重打进安装包；`transformers.js` 在 Node 下跑 8B 视觉模型不现实。
- Ollama 本身就是开源的模型服务，提供 OpenAI 兼容协议，模型按需拉取 —— 它满足"内置"的实质：装好 DeepThink 就能用，配置由系统自己写。

保留出口：`DEEPTHINK_LOCAL_MODEL_URL` 可改地址（换端口 / 指向另一台机器），`ocr.json` 的 `baseUrl` 可显式指向任意 OpenAI 兼容视觉服务。

### 3.3 已装 Ollama 但服务没起时怎么办

**提供显式的「启动服务」按钮，不在开机时自动拉起。**

- `spawn(ollama, ['serve'], {detached: true})` + `unref()`，服务进程生命周期不跟随 DeepThink 主进程。
- 不做成开机自动：那是持久化机制，影响面超出本需求，且用户机器上 Ollama 通常由 brew services 托管，重复拉起会抢端口。

### 3.4 向量维度：写死 vs 问出来

**问出来。** 写配置前调一次 `/v1/embeddings` 读 `data[0].embedding.length`。

维度一旦写错，`vec0` 虚拟表建出来就是错的（sqlite-vec 在建表时固定维度），而且要等到用户第一次检索失败才会暴露。代价是一次 20ms 的请求。

### 3.5 扫描件上传：同步 OCR vs 后台 OCR

**后台。** 287 页 × 每页数秒 ≈ 半小时，同步做必然超时，且失败时用户看到的是"上传成功但列表里什么都没有"，比原来的明确报错更难排查。

代价：需要一份「正文待定」的文档行，异步补正文。这引入了两个必须处理的问题（见 TECH_SOLUTION §4.3）：

- 占位 `content_hash` 不能是空串的 hash —— 两份待 OCR 的扫描件会被去重逻辑判成同一份；
- 真正的去重推迟到正文落库时，此时才发现重复要给出明确说明而不是留一份永远 pending 的文档。

## 4. 用户故事

### US-1 上传扫描件（普通用户）

> 我是知识库用户，手上只有扫描版 PDF。我点「上传文档」，选了文件。

- 上传接口 1 秒内返回，提示「已上传。这是扫描件，正在后台 OCR 识别，耗时取决于页数，可在列表中查看进度」。
- 文档列表里该行显示黄色 `OCR 识别中` 徽标 + `ocr 12/287` 实时进度。
- 480p 页跑完后自动转入 `向量化中` → `就绪`，`分块 > 0`，`已向量化 > 0`。

**前置条件未满足时**（OCR 未启用 / 视觉模型没下载 / 本机服务没起），上传**当场**返回 400 并说明该去设置页做什么 —— 不让用户等半小时才看到失败。

### US-2 启用本机向量模型（管理员）

> 我是管理员，没有 OpenAI / 智谱的 API Key，但想让知识库能语义检索。

- 进入「设置 → Embedding 配置」，最上方是「本机内置模型服务」面板。
- 服务状态显示绿色「服务可用 · http://127.0.0.1:11434 · v0.40.3」。
- 向量模型一行显示 `bge-m3` 未安装 → 点「下载」→ 进度条走完 → 按钮变成「一键启用」。
- 点「一键启用」→ 提示「已启用本机向量模型 bge-m3（1024 维）」；若维度发生变化，追加提示「请到各知识库点『重建索引』」。

### US-3 启用扫描件 OCR（管理员）

> 同上，在同一个面板的「扫描件 OCR」一行点「下载」`qwen3-vl:8b`，装好后点「启用」。

- 关闭状态下再次上传扫描件会被拒绝并提示去启用。

## 6. 风险

| 风险 | 影响 | 处理 |
|---|---|---|
| 视觉模型 OCR 质量不达标（尤其小字中文表格） | 入库文本有错字，检索命中率下降 | e2e 用真实扫描件抽验；保留 `ocr.json` 的 `model` 可换（minicpm-v / qwen2.5vl 等） |
| 大文件 OCR 时长过长 | 用户以为卡死 | 进度落库 + 列表显示 `ocr N/M`；`maxPages` 上限 300 并在正文留痕 |
| 页眉页脚在每页重复，污染索引 | 检索噪声 | **本次不处理**，列为已知限制（去重规则容易误删正文，需要单独的判断依据） |
| 切换向量维度清空已有向量 | 老库检索退化 | 接口返回 `dimensionChanged`，UI 明确提示「重建索引」；9999 切换时本就没有向量（0 命中），无损失 |
