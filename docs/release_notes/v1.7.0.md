# DeepThink v1.7.0 发布说明

> 自托管的多用户本地 AI Agent Loop Engineering 系统（支持桌面端 + 浏览器 + 移动端）
> Powered By AI Genius Institute，AI 光剑

发布日期：2026-10-13

v1.7.0 是一个**可观测性收口**版本，主轴是新模块 **Agent 运行监控（Agent Runtime Monitor）**：把散落在 8 张表、5 套读接口里的 Agent 运行数据聚合为一个统一的「运行」抽象，给出总览 KPI、趋势汇总、跨来源运行列表与单次运行的时间线轨迹；同时为**开放平台 AaaS** 补齐它此前完全缺失的运行记录。

在此之前，平台能跑的东西已经很多——对话 / IM Agent、图编排（Swarm / Workflow）、Loop Engineering、监督者、定时任务、沙箱、Harness 评测、开放平台 AaaS——但它们的 trace **各写各的表、各开各的接口**（`/api/groups/:jid/trace/*`、`/api/graph/runs/*`、`/api/loops/:id/trace` …）。**没有一个地方能回答「现在系统里有哪些 agent 在跑、跑得怎么样、最近趋势如何」**。开放平台更极端：每次调用只在 `usage_records` 落一行用量，**没有状态、没有错误、没有轨迹**——即便是对外交付的「Agent 服务」，也没有任何可监控的运行记录。

本版本共 **5 个 commit**，**Schema v71 → v72**（新增 `open_platform_runs` 表，迁移自动执行），无破坏性 API 变更。

## 🎯 新能力：Agent 运行监控模块

需求与验收标准见 [`docs/prd/agent-runtime-monitor/PRD.md`](../prd/agent-runtime-monitor/PRD.md)，技术方案见 [`docs/tech_solution/agent-runtime-monitor/TECH_SOLUTION.md`](../tech_solution/agent-runtime-monitor/TECH_SOLUTION.md)。

### 统一「运行」抽象：8 条链路收敛为一个视图

模块把 8 个来源归一为同一个 `RunSummary`，每条运行都带统一的 `runId`（`{source}:{nativeId}`）、归一化状态、耗时、tokens、成本、归属人与可读的工作区 / Agent 名：

| # | 来源 | 主表 | 轨迹表 | 归一前状态词表 |
|---|------|------|--------|---------------|
| S1 | 对话 / IM Agent | `chat_trace_nodes`（`node_type='turn'` 且无父节点 = 一次运行） | 自身子树 + `trace_tool_calls` | `done / running / failed` |
| S2 | 图编排（Swarm / Workflow） | `graph_runs` | `graph_node_runs` | `completed / paused / cancelled / …` |
| S3 | 开放平台 AaaS | **`open_platform_runs`（本版本新增）** | `trace_steps` | `completed / running / failed` |
| S4 | Loop Engineering | `loop_runs` | `loop_trace_nodes` + `loop_iterations` | `reviewing / iterating / …` |
| S5 | 监督者 Supervisor | `supervisor_sessions` | `supervisor_decisions` | `active / paused / aborted` |
| S6 | 定时任务运行 | `task_run_logs` | 自身（每行即一次运行） | `success / error / …` |
| S7 | 沙箱代码执行 | `sandbox_executions` | 自身 | `success / ok / timeout / …` |
| S8 | Harness 评测运行 | `harness_eval_runs` | 自身（+ `trace_node_root_id`） | `completed / failed` |

**状态词表逐源不同**（`done` vs `completed` vs `success`），因此每个来源都显式声明自己的映射表，归一到 `running / success / failed / cancelled / pending` 五档后才允许参与聚合——这是本模块 P0 级的正确性要求，也是跨源统计能成立的前提。

### 八个能力面

| 面 | 能力 |
|---|---|
| **F1** 总览 KPI | 8 张卡片：运行中 / **疑似卡住** / 成功 / 失败 / 成功率 / 总 tokens / 总成本 / P95 耗时；`running` 且已跑超 30 分钟的运行被标为「疑似卡住」并以警示色高亮。窗口 24h / 7d / 30d 可切（默认 7d） |
| **F2** 趋势汇总 | 按时间桶（24h → 小时桶，7d/30d → 天桶）给出运行数 / 失败数 / token / 成本趋势，**空桶补 0 不塌陷**（x 轴连续）；另附来源维度与工作区 / Agent 维度分布 |
| **F3** 统一运行列表 | 跨全部来源的一张表（状态 / 来源 / 标题 / 工作区 / 归属 / 耗时 / Token / 成本 / 开始时间），支持来源多选、状态、时间范围、关键词筛选与分页 |
| **F4** 单次运行详情 | 抽屉式面板，展示 `RunSummary` 全字段 + 该次运行的**时间线轨迹**（节点类型 / 标题 / 状态 / 起止 / 耗时 / 入参出参）；打开不整页刷新，关闭后列表滚动位置保持 |
| **F5** AaaS 运行埋点 | 新增 `open_platform_runs` 表，在 `runAgent()` / `streamAgent()` 两条链路记录每次调用：状态流转、`trace_id`、tokens / 成本 / 轮数（与计费账本**同源 SDK result**）、错误文本、请求 / 响应摘要 |
| **F6** 实时刷新 | 默认 5s 轮询；**`document.hidden` 时暂停轮询，切回前台立即补一次** |
| **F7** 权限与隔离 | 沿用平台 RBAC：admin 可见全部，member 只可见自己有权访问的工作区；越权访问单条运行返回 **404 而非 403**（403 会泄露「该 runId 存在」） |
| **F8** 导航入口 | 左侧导航新增「运行监控」→ `/runtime-monitor`（懒加载路由，整页刷新直达不 404） |

**入口**：Web 导航「运行监控」→ `/runtime-monitor`。后端 4 个只读端点：`GET /api/runtime-monitor/{sources,overview,runs,runs/:runId}`（趋势桶、来源分布与工作区分布都随 `/overview` 一次返回，不另开端点）。

### 落地取舍（Think Before Coding：显式暴露）

| 决策 | 取舍 |
|---|---|
| **归一化只发生在读侧** | 除开放平台 AaaS 新增运行记录表外，**不改任何既有写入路径**——8 条来源链路的写入行为零改动，监控挂掉不影响业务。代价是每次查询要做跨源 `UNION ALL`，靠索引与 12005 行规模下的 P95 实测兜底 |
| **chat 没有权威「运行」边界** | `chat_trace_nodes.session_id` 实测恒为 NULL（`src/flm/flm-collect.ts` 有同款实测注释），无法按会话对齐，因此以 `node_type='turn' AND parent_node_id IS NULL` 作为运行根并**在文档中明示口径**，不假装它权威 |
| **`trace_steps` 不单独作为来源** | 它是步骤明细（thinking / compact / llm_call …）而非运行，且线上绝大多数行 `status='running'` 无 `ended_at`——作为 S1 / S3 的轨迹明细并入，不单列 |
| **Eval Center 不纳入** | 其 `agent_trace` / `trace_span` 建在**独立 `pg.Pool`** 上，表只在 PostgreSQL 存在，SQLite 实例里根本没有这两张表；且它已有自己的轨迹 UI（`/eval-center`） |
| **不做实时推送** | 用 5s 轮询而非 WebSocket：本模块是只读聚合视图，轮询让「刷新」语义简单可验证，也避免给 WS 广播再加一类高频消息 |

### 勘察到的字段语义坑（已写进约束，避免回归）

- **`chat_trace_nodes.session_id` 恒为 NULL** → 会话对齐必须用 `chat_jid` + 时间窗口。
- **`chat_trace_nodes.id` 是 per-jid 自增**（`UNIQUE(chat_jid, id)`），跨 jid 不唯一 → chat 的 `runId` 必须带 `chat_jid` 前缀（`chat:{chat_jid}#{nodeId}`），否则详情页会取到别人的运行。
- **`graph_node_runs.status` 的 CHECK 在 v57 迁移后含 `cancelled`**，早期 DDL 注释不含——只信迁移后的约束。
- **空来源必须降级为空集而非 500**：目标实例上 8 个来源里有 5 个是 0 行（Loop / 监督者 / 定时任务 / 沙箱 / Harness），缺表与空表都要能正常渲染。

## 🐛 验收阶段发现并修复的 4 起缺陷

同样地，这 4 起**全部在单元测试全绿、接口全部返回 200 的情况下存在**——它们长在单测够不到的地方：**前端是否真的渲染了后端算好的数**、**用户能否走到某个分支**、**浏览器信号是否被处理**。

| # | 现象 | 根因 | 修复 |
|---|------|------|------|
| 1 | 同一批 AaaS 运行，KPI 分布里叫 `open-platform`，运行列表里叫 Agent 名；**多个 Agent 的运行被压成一行** | 分布按 `workspace` 分组，而开放平台的 `workspace` 是**常量哨兵** | 分组表达式改为 `CASE WHEN source='open-platform' THEN agent_id ELSE workspace END`；新增 3 条断言并**反向验证**（还原成 `workspace` → 3 条全红） |
| 2 | 页面渲染不出「总成本」，尽管后端已算好 `kpis.costUsd` | **纯前端漏渲染**：API 有、UI 无 | 补一张 KPI 卡（共 8 张，与 AC-F1.1 对齐），UI 断言 8 个标签齐全 |
| 3 | 来源分布只显示**有数据**的来源，用户无法点选当前为空的来源 | 前端只拿 `overview.bySource`，没有完整来源清单 | 新增只读端点 `GET /api/runtime-monitor/sources` 吐来源注册表（前端不再抄一份名字）；chips 以注册表为骨架，8 个来源恒在，空来源显示 0 |
| 4 | `document.hidden` 时仍在每 10s 打后端 | 轮询未处理页签可见性——**PRD 的 AC-F6.3 写了，但实现漏了** | 照 `ChatView.tsx` 的既有模式加可见性守卫；实测可见 13s = 2 次请求、隐藏 13s = **0** 次、切回 2.5s = 2 次 |

**缺陷 3 是「功能写了但用户走不到」的典型**：空来源降级逻辑本身是对的，但入口只渲染有数据的来源，于是「点一个空来源看降级表现」这条验收路径在 UI 上**根本不可达**——T6 场景此前只能靠后端单测覆盖。

另修正 1 处**代码注释里的假事实**：`run-recorder.ts` 曾声称非流式路径收不到流式事件；实测两条路径共用 `buildQueryOptions` 且 `includePartialMessages` 恒为 true，已用真实工具 span 佐证后改正注释。

### 文档与实现不符的 3 处（已按实测修订，非代码缺陷）

验收过程中发现需求文档本身写错了三处，全部以实测证据修订 PRD 与测试用例，而不是让实现去迁就文档：

| 处 | 原表述 | 实测真相 |
|---|--------|---------|
| `AC-F5.3` / T5 | 「无效 agent id 也落 `status='failed'` 行」 | **被拒请求（404 / 403）不落行**——运行记录在 `resolveAgent` 通过之后才建（`agent-service.ts:256`）。被拒的请求没有运行过，为它建行只会污染监控列表；真被拒的调用方自己就会看到 404 / 403。实测两个被拒场景行数均 +0 |
| T5 对账 | 未说明账号角色 | **必须用非 admin 用户**：`billing.ts:66` 对 admin 豁免计费（`// admin 豁免：不计量、不扣费`），admin 名下 Agent 的 `usage_records` **恒为 0 行**。改用真实注册的 member 用户后，四个同源字段才闭环一致 |
| T5 `duration_ms` | 期望两个账本相等 | **两个账本刻意不同，不做相等断言**：运行记录是平台侧**墙钟**（`Date.now() - startedMs`），计费账本是 **SDK 自报**（`event.duration_ms`）。保留差异的理由：① 墙钟与 `started_at`/`ended_at` 精确自洽；② 失败 / 超时路径收不到 SDK 的 `result` 事件，只有墙钟可用；③ `usage_records` 是计费账本，改口径会波及计费，超出本需求范围。**已知代价**：监控页与计费明细对同一次运行会显示两个耗时数字——这是取舍，不是缺陷 |

## 🐛 迭代 2：运行轨迹只显示 3 行，无法展开（用户反馈驱动的修复）

模块交付后收到用户反馈——`/runtime-monitor` 运行详情里的「运行轨迹」，每一步的入参 / 出参**都被截断成 3 行并以 `…` 结尾，界面上没有任何展开入口**。走 **Issue 修复流程**（不是新需求），复盘见 [`docs/issues/2026-10-13-runtime-monitor-trace-truncated.md`](../issues/2026-10-13-runtime-monitor-trace-truncated.md)。

**根因是纯展示层的 CSS**：轨迹行用了 Tailwind `line-clamp-3`（展开即 `display:-webkit-box; -webkit-line-clamp:3; overflow:hidden`），**数据完整在 DOM 里、后端 payload 也完整**，只是视觉被裁且不可逆。因此本次**不改后端、不改数据库、不改写入路径**——只给展示层加一个开关，单文件 +53 / −8。

**问题的真实规模（实测，不是个别现象）**：隔离快照 7 天窗口扫 20 条运行，**12 条**的轨迹存在被截文本；抽样那条长运行（4518 步）**1595 个字段被裁**，累计隐藏 **192080 px** 内容。部署到生产后复测：7 天窗口的 **12 条运行全部**存在视觉裁切——**用户看到的每一条运行都在被裁**。

**修复的四个设计选择**：

- **整条轨迹一个开关，而不是每行一个按钮**：既然 12/20 条运行、6669 个字段里 1595 个被裁，逐行按钮等于让用户点几十次，还会在绝大多数行上挂一个按钮噪声。
- **状态存 `expandedRunId` 而不是裸 `boolean`**：抽屉会在不关闭的情况下被切换运行，存 runId 天然表达「只有这条运行处于展开态」，**不需要 effect 去重置**，也就不会出现「换了一条运行但还停在展开态」的残留帧。
- **无入参出参的原子运行不渲染按钮**：`task / sandbox / harness-eval` 的记录入参出参都为空，给它们一个「点了没反应」的死按钮不如不给。
- **不动写入侧的截断上限**：展开只能展开到**库里存了的内容**。实测的写入上限是既有设计——对话 `thinking` 步 **500** 字符（`trace-node-allocator.ts:316,324`，生产 119 行中 **108 行已触顶**）、`turn` 步 **400**（`agent-runner/src/index.ts:2413`）、AaaS 摘要 **500**（`run-recorder.ts:26`，注释写明「监控表不该成为用户数据的第二份副本」）。改它要牵动 agent-runner 与对话存储量，且**已落库的行也救不回来**，按 Surgical Changes 原则仅登记不改。

**验证是 A/B 的**：把改动 patch 掉、用**同一份数据**重建 web 再跑同一脚本，前 5 步照常通过（现象如实复现），第 6 步**红在「轨迹区没有展开按钮」**——即旧代码下用户的确无路可走。展开后 6669 个入参 / 出参元素全部 `-webkit-line-clamp: none`，`scrollHeight > clientHeight` 的溢出元素 **0 个**，内容与后端 payload **逐字一致**；再点「收起」全部回到 3 行。生产 `localhost:9999` 部署后复测同样全绿。

> 本轮的三个方法论教训已沉淀进 issue 文档 §8：① `line-clamp-N` 是**单向**截断，长文本展示必须同时交付展开入口；② **验「文本有没有被裁」不能搜 DOM 文本**（`textContent` 在 CSS 裁剪下仍是全文，会给出假阳性），正确判据是几何量 `scrollHeight > clientHeight`；③ **A/B 的选择器必须新旧两边都存在**，否则「红」的理由是选择器找不到元素，证明不了任何事。
