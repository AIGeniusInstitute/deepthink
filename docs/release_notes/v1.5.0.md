# DeepThink v1.5.0 发布说明

> 自托管的多用户本地 AI Agent Loop Engineering 系统（支持桌面端 + 浏览器 + 移动端）
> Powered By AI Genius Institute，AI 光剑

发布日期：2026-09-24

v1.5.0 是一个**聚焦修复**的版本，主轴只有一条：**让 v1.4.0 交付的 Agent Group Chat（Swarm）从「界面、数据模型、Pipeline 面板都在，但执行链路从未接线」变成真正可用**。

v1.4.0 把 Swarm 作为企业协作工作负载之一交付了出去——群组、席位、消息、Pipeline 面板的界面与表结构都已完成，但「一条消息如何变成一次真正的席位发言」这一段代码**完全没有落地**。用户实际遇到的是三个叠加的失效：

- **发消息零执行**：消息落库了，但没有任何东西被触发，席位不回复，Pipeline 面板永远为空；
- **执行了也看不到**：即使后端跑出了结果，前端拿到的是**空气泡**，且不流式，只有手动刷新才整段出现；
- **能力不对等**：普通对话能挂的技能 / MCP 工具 / 知识库，群组席位一概没有。

v1.5.0 把这三条一次补齐，并顺手把这段临时链路整体删掉、回归平台既有的图谱引擎（`src/graph-engineering/`）——**不引入新引擎、不新增中间件、不新增依赖**。

本版本共 **2 个修复 commit**（另含 2 个 merge commit），**无 schema 变更**（v70 → v70），无新增迁移。

## 🐛 缺陷修复

### 一、Agent 群组发消息无任何回复，Pipeline 面板为空（`eac32e8`）

完整复盘见 [`docs/issues/2026-09-23-agent-group-message-no-response.md`](../issues/2026-09-23-agent-group-message-no-response.md)。

**用户现象**：在群组页输入框发消息，气泡出现了，但没有任何席位回复；右侧 Pipeline 面板始终停在「点击"启动 Pipeline"开始运行」，点按钮也没反应；刷新后消息还在，依然没有回复。

**根因**（三重叠加，全部有库表/日志证据）：

1. **`POST /:jid/messages` 只写库不执行** —— 只调 `createGroupMessage(...)`，不触发任何执行。故障时 `group_messages` 有 3 行（全是 `sender_type='user'`），而 `graph_runs` / `graph_definitions` **均为 0 行**——「消息进来了，但没有任何东西被执行过」。
2. **「启动 Pipeline」按钮必然失败** —— 硬编码 `definition_id='swarm-pipeline', version=1` 插入 `graph_runs`，而 `graph_definitions` 表是空的，触发 `FOREIGN KEY constraint failed`；连带 `createPipelineNode` 同样失败，面板永远没有节点。
3. **唯一的派发通道是 Redis，本机不可用** —— `src/redis-bus.ts` 的 `publishAgentTask` 在未连接时**直接 `return true` 却什么都没做**，而该路由没有本地兜底路径，于是接口返回 `status:'running'` 而实际零执行。这是本次最隐蔽的一环：**「接口返回成功」≠「真的执行了」**。

另修复新群组首条消息被消息轮询的冷启动守卫**静默丢弃**的问题（新 workspace 不播种 cursor，首条消息直接被快进跳过）。

**修复方案**：删掉整段临时 Redis 链路（`loadSwarmAgentDefContent`、`createPipelineNode`、`updatePipelineNode`、`subscribeIpcOutput` / `publishAgentTask`），回归技术方案原本的设计——**一个 swarm 群组就是一个 `graph_definition`：节点是席位，边是发言顺序**。

### 二、Agent 群组对话无流式输出、席位不继承技能 / MCP / 知识库（`e32c9a7`）

完整复盘见 [`docs/issues/2026-09-24-agent-group-no-streaming-output.md`](../issues/2026-09-24-agent-group-no-streaming-output.md)。

承接上一个 issue：修好「席位根本不执行」之后，本 issue 修的是「执行了但用户看不到」。

**用户现象**：席位气泡是**空的**（有框有头像，就是没字）；回复不流式，只有刷新后才整段出现；输入框上方没有技能 / MCP / 知识库工具栏。

**根因**：

1. **前端只处理一种事件类型** —— `GroupChatArea` 的 WS 处理器只认 `group_message_created`，席位的 `text_delta` 被直接丢弃。
2. **同一份数据在两处用了两个字段名** —— WS 事件（`swarm-runner.ts`）用 `content`，REST（`msgToJson`）用 `contentRef`；前端把前者原样塞进后者的类型里，一个 `as GroupMessage` 断言把这条缝盖住了 → **永远是空白气泡**。刷新走 REST 所以能看到历史，实时追加的那条永远是空的。
3. **原始流事件不自解释** —— 席位的 `text_delta` 只带一个不透明的 `turnId`（`graph-xxx-seat-1`），不带座位号，前端没有任何办法把这段文字归属到某个席位。
4. **席位合成群组不带 owner 身份** —— `buildOwnerGroup` 只设了 `owner_user_id`（`RegisteredGroup` 根本不读这个字段），`created_by` 长期为 `undefined`。而 `applyTurnMounts` / `loadUserPlugins` / 用户级全局记忆**全部以 `group.created_by` 为 owner 依据** → 即使传了挂载也解析不到归属。

**修复方案**：不新造流式通道，复用普通对话那条链路。后端把席位节点的流事件翻译成带座位号的 `group_message_delta`，前端按普通聊天的方式逐字累积渲染；挂载复用 `startGraphRun` 已有的 `initialState` 加性通道，落到既有的 `applyTurnMounts`；工具栏直接复用普通对话的 `ChatToolbar` + `chat-mounts` store + `selectedMounts` 字段，**不新写「群组版」组件**。

另修复席位执行模式未继承创建者主容器模式的问题——此前落到 `'container'` 默认值，导致「管理员自己在 host 跑得好好的，他建的群组却在容器里连不上自己的 provider」。

## 🔩 架构收敛：swarm 不再是独立执行链路

本次最大的结构性改动不是修哪一行，而是**删掉了一条并行的、重复的、且从未真正跑通的执行链路**，让 Swarm 回归平台统一的图谱引擎：

| 维度 | 修复前 | 修复后 |
|---|---|---|
| 执行引擎 | 临时 Redis 链路（独立实现） | 既有 `graph-engineering` 引擎 |
| 席位 → 执行 | 无映射 | 席位即图节点（`seat-<id>`），发言顺序即边 |
| 定义存储 | 硬编码 `'swarm-pipeline'`（表为空） | `registerDefinition()` 真实注册，版本自增 |
| 流式输出 | 仅落库后一次性事件 | `text_delta` → 带座位号的 `group_message_delta` |
| 挂载能力 | 无 | 复用 `applyTurnMounts`（技能 / MCP / 知识库） |
| 失败语义 | 无 Redis 也返回 `running` | 返回真实 `runId` 或明确 `error` |

新增 `src/agent-group/swarm-definition.ts`（席位 → 图谱定义）与 `src/agent-group/swarm-runner.ts`（触发 + 席位输出回写）。图谱引擎侧只做**加性**改动：新增两个可选钩子 `onNodeSettled` / `onNodeStream`（未接线即 no-op，对既有 graph run 零影响），以及读取 `state.goal` 注入用户消息（无 `goal` 时行为完全不变）。
