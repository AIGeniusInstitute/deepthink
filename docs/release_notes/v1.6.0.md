# DeepThink v1.6.0 发布说明

> 自托管的多用户本地 AI Agent Loop Engineering 系统（支持桌面端 + 浏览器 + 移动端）
> Powered By AI Genius Institute，AI 光剑

发布日期：2026-10-10

v1.6.0 是一个**新能力落地**版本，主轴是新模块 **FLM（Feedback & Learning Module，反馈与学习自进化模块）**：把一次任务的真实结果——用户评价、运行日志、环境变化——转成结构化反馈事件，经三层评价与失败归因，沉淀为可复用的经验与策略版本，并通过门禁 + 灰度 + 自动回滚安全地作用于下一次任务。

在此之前，平台已经能「执行」与「观测」（trace / eval-center / autonomy），但**从结果回流到下一次行为的闭环是断的**：用户对一条回复的评价没有任何落点（`messages` 表无评价列，消息气泡无评价按钮），失败无法归因到具体环节，策略变更只有全量翻转、没有灰度。FLM 补齐的正是这三块空白。

同时本版本修复了一批缺陷，其中最值得单独提出的是**验收阶段发现的 8 起产品缺陷**——它们全部在单元测试全绿、接口全部返回 200 的情况下存在，属于单测结构上够不到的位置（前端消费、上下游契约、事件循环、操作可重复性）。这 8 起是本版本在「交付」之外真正花时间的地方。

本版本共 **34 个 commit**（含 4 个 merge），**Schema v70 → v71**（新增 12 张 `flm_*` 表，迁移自动执行），无破坏性 API 变更。

## 🎯 新能力：FLM 反馈与学习自进化模块

需求与验收标准见 [`docs/prd/feedback-learning-module/PRD.md`](../prd/feedback-learning-module/PRD.md)，技术方案见 [`docs/tech_solution/feedback-learning-module/TECH-SOLUTION.md`](../tech_solution/feedback-learning-module/TECH-SOLUTION.md)。

FLM 是位于「行动执行」之后、「再规划」之前的**闭环能力中枢**，六个能力面：

| 面 | 能力 | 落点 |
|---|---|---|
| **F0** | 降级与可观测 | 一键开关（`flm_config.enabled`）；关闭后采集/评价全停，Agent 按「无反馈执行」正常运行，用户无感 |
| **F1** | 反馈采集 | 用户反馈（👍/👎 + 六类原因标签 + 纠错文本 + 隐式行为信号）、系统日志（工具调用回执 / 错误码 / 耗时 / 重试 / token 消耗，带采样率与字段白名单）、环境数据（观测点注册 + 前后快照 diff + 有效期） |
| **F2** | 统一分析框架 | 三类来源归一化为同一 `FeedbackEvent`；四级主键实体对齐（缺失时时间+内容兜底并显式标记 `alignment='fallback'`）；时序对齐；来源权重 × 置信度冲突消解；时间窗去重；五类脱敏规则**可热更新** |
| **F3** | 三层评价引擎 | 结果层三档（`achieved / partial / failed`）、过程层（路径符合度 / 耗时 / 重试 / 首个异常步骤）、质量层六维（事实性 / 格式 / 时延 / 成本 / 安全 / 偏好匹配）；失败归因到 `intent / planning / tool_selection / param_gen / execution / summary` 六环节；**每个结论附证据片段** |
| **F4** | 学习与自进化 | 短期纠偏（重试上限 + 退避 + 工具白名单 + 耗时闸门，超限降级人工）、经验记忆（正负样本 + 向量检索 Top-K）、策略优化（prompt / routing / param / fewshot 四类版本）、数据回流（chosen/rejected 偏好对 + SFT 语料，带来源与时间可导出）、知识库自更新（纠错反馈 → 知识候选 → **审核后**入库） |
| **F5** | 闭环执行与安全 | 版本管理（变更内容 / 触发来源 / 关联归因标签 / 父版本）、**回归评测门禁**（核心指标劣化超阈值即拦截并给出劣化明细）、灰度放量（按流量比例，最小 1%）、**自动回滚**、安全类变更强制人工审核、全链路审计时间线可回放 |
| **F6** | 运营观测控制台 | 总览看板（反馈量 / 满意度 / 成功率 / 纠偏率 / 闭环时延）、归因多维下钻、案例检索与人工修正归因、策略版本 A/B 对比与放量建议、阈值告警 |

**入口**：Web 导航「自进化」→ `/feedback-learning`（7 个页签的控制台）；聊天消息气泡上的 👍/👎 组件（全模式与紧凑模式均有，分享视图隐藏）。

### 落地取舍（Think Before Coding：显式暴露）

| 原始口径 | 本次口径 | 理由 |
|---|---|---|
| 「支持亿级日写入」「千万级向量检索」 | 不承诺压测绝对值；实现为可配置采样 + 索引 + 分页，报告中标注**未压测** | 单机 dev 实例产生不了亿级数据，承诺绝对值即为不可验证的过度承诺 |
| 「跨租户隔离」 | `tenant_id` 字段预留并落库，隔离边界落在**用户 / 会话**级（与平台既有模型一致） | 本平台无显式租户实体，凭空造租户体系属过度设计 |
| 「LLM-as-Judge 与规则判定双轨」 | **规则轨必须可用且为默认**；LLM 轨为可选（每次评价显式开启），不可用时降级为单轨并如实标注 `evaluator` | 保证验收可复现、不依赖外部模型网络 |
| 「数据集回流模型训练平台」 | 产出落库 + 可导出的偏好数据集与 SFT 语料；**不实现**训练平台对接 | 原文非目标已明确「不自建训练基础设施」 |
| 「环境数据全量快照 + 增量订阅」 | 观测点注册 + 前后快照 diff + 有效期；**不实现**对外部业务系统的实时订阅连接器 | 连接器需业务侧契约，属外部依赖 |

### 复用而非重造（侦察结论，均带证据）

落地前先摸清了既有能力，避免重复造轮子：

| 既有能力 | 与 FLM 的关系 |
|---|---|
| `chat_trace_nodes` / `trace_steps` / `trace_tool_calls` | **复用为 TaskTrace**，不新建轨迹表 |
| `src/embedding.ts`（`embedText` / `cosineSim`） | **复用**为经验记忆的索引底座 |
| `src/eval-center/eval-scoring.ts` | **不复用** —— eval-center 评的是 golden test case，FLM 评的是线上真实任务，输入与结论语义不同 |
| `src/harness-registry.ts` | **不复用** —— 其版本单元是 harness manifest，且只有全量翻转、无灰度 |
| `src/autonomy/autonomy-learning.ts` | **不复用** —— 其单元是单次运行的教训文本，无正负样本类型、无归因环节、无复用计数 |

FLM 的**独占价值**是六块：①消息级用户反馈通道 ②三类来源统一归一化 ③三层评价与失败归因 ④正负样本经验记忆 ⑤带灰度的策略版本闭环 ⑥运营控制台。其余一律复用既有底座。

### 实测约束反向决定设计

动笔前对本机实例做了数据探查，四条结论直接改变了实现形态：

| 实测结论 | 影响 |
|---|---|
| `chat_trace_nodes.session_id` 9092 行**全为 NULL** | 节点无法按 session 对齐，只能 `chat_jid + 时间窗` |
| `messages.task_id` 330 行**全为空** | 任务单元不能依赖既有 `task_id`，须自建推导规则 |
| `trace_tool_calls.chat_jid` 全填充 | 工具调用可稳定按聊天 + 时间窗捞取 |
| 所有时间列统一 ISO-8601 UTC 文本 | 可直接字符串比较做范围查询，SQLite / PG 行为一致 |

由此定义四级任务单元前缀，保证 `taskId` 永不为空：

```
turn:{turn_id} > sess:{session_id} > msg:{message_id} > chat:{jid}:{hourBucket}
```

`turn:` 的窗口起点取本回合**最早**的消息（用户提问）而非助手回复——轨迹节点发生在「提问 → 回复」之间，用回复时间当起点会把整段轨迹排除在外。

### 数据模型

12 张 `flm_*` 表，全部落在主数据库（SQLite / PostgreSQL 双兼容）：`flm_feedback`、`flm_events`、`flm_evaluations`、`flm_cases`、`flm_strategies`、`flm_actions`、`flm_observations`、`flm_snapshots`、`flm_config`、`flm_alerts`、`flm_audit`、`flm_knowledge`（知识条目候选与审核状态）。

SQL 双兼容约束（踩过的坑，写进约束避免回归）：

- **不用** `ADD COLUMN IF NOT EXISTS` —— PG 专有语法，会打断 SQLite 批处理 → 改用 `ensureColumn()`（基于 `PRAGMA table_info`）
- **不用** `ON CONFLICT ... DO UPDATE` —— `sql-translator.ts` 覆盖不全 → 改用 `INSERT OR REPLACE`
- 不用 `jsonb` / `now()`；JSON 统一存 TEXT；时间统一 `Date.now()` 毫秒整数

## 🐛 验收阶段发现并修复的 8 起产品缺陷

这是本版本在「交付新能力」之外真正花时间的地方。8 起缺陷**全部在单测全绿、接口全部 200 的情况下存在**——单测覆盖的是后端纯函数产出，而缺陷长在**前端消费、上下游契约、事件循环、操作可重复性**这四处单测够不到的地方。

| # | 缺陷 | 症状 | 根因类别 | Issue 文档 |
|---|---|---|---|---|
| 1 | 反馈去重把不同消息并成一条 | 多条不同反馈互相覆盖 | 去重键选错 | [`2026-10-10-flm-feedback-dedup-…`](../issues/2026-10-10-flm-feedback-dedup-collapses-distinct-messages.md) |
| 2 | 评价从不落库 | 「从评价中沉淀」永远 0 条 | `insertEvaluation` 零调用点 | [`2026-10-10-flm-evaluations-never-persisted.md`](../issues/2026-10-10-flm-evaluations-never-persisted.md) |
| 3 | 工具调用失败信号全链路无人识别 | 三类归因分支线上从未触发 | 生产者 / 消费者状态取值集合交集为空 | [`2026-10-10-flm-toolcall-failure-…`](../issues/2026-10-10-flm-toolcall-failure-signal-never-detected.md) |
| 4 | 「学习沉淀」页签 `undefined.toFixed()` 打白整个控制台 | 点一次该页签，7 个页签全部不可用 | 前端 interface 声明了后端不存在的字段 | [`2026-10-10-flm-learning-tab-crash-…`](../issues/2026-10-10-flm-learning-tab-crash-blanks-console.md) |
| 5 | 案例检索渲染三个不存在的字段 | 「相似度 NaN%」+ 标题空白 | 同上（检索接口与列表接口形状混用） | 同上 §2.1 |
| 6 | 案例库随每次沉淀膨胀，Top-K 返回重复候选 | Top-5 = 同一条案例的 5 份拷贝 | 派生数据缺幂等键 + 检索未去重 | [`2026-10-10-flm-case-library-…`](../issues/2026-10-10-flm-case-library-duplicates-and-topk.md) |
| 7 | `/admin/data-feedback` 同步计算约 3.8s **冻结 Node 事件循环** | 该接口被调用期间，**同进程内所有其它 API**（含 192 字节的 `/health`）一起卡住 | 请求路径上的同步 CPU 密集计算 | [`2026-10-10-flm-data-feedback-…`](../issues/2026-10-10-flm-data-feedback-blocks-event-loop.md) |
| 8 | 加载失败被渲染成「暂无数据」 | 库里 53 个版本时页面显示「暂无策略版本」 | catch 只发 toast 不落 state + 空态文案是一次**事实断言** | [`2026-10-10-flm-load-failure-…`](../issues/2026-10-10-flm-load-failure-rendered-as-empty-state.md) |

**缺陷 7 是本轮最隐蔽的一起**：它不产生任何错误，只是让**别的**接口变慢，因此最初表现为三个互不相关的用例（TC-17/18/28）超时。取证方式是并发探测——在 `/admin/data-feedback` 执行 0.3s 后发一个 192 字节的 `/health`，实测耗时 3.46s；单独测 `search` 只要 13ms。修复（目标文本级记忆化）后：data-feedback **3.83s → 0.041s**，健康探测 **3.46s → 0.16s**，且输出逐位不变。

**缺陷 4/5/8 是同一族**：一个故障的表现形式与某种正常状态完全同形。缺陷 4 表现为白屏（明显）、缺陷 5 表现为「NaN%」（也明显），而缺陷 8 表现为**一句自信的「暂无数据」**——最危险，因为它把偶发故障永久升级成了错误结论。

### 判别力验证（如实标注做到哪一步）

不满足于「改完测试还是绿的」，而是**把修复撤掉、确认新测试确实转红**，再还原：

| 缺陷 | 回归测试位置 | 撤掉修复后的结果 |
|---|---|---|
| 3 | `tests/units/flm-evaluate.test.ts` · `FLM F3 · 上游状态契约` | 3 条中 2 条转红 |
| 4 | `tests/units/flm-learn.test.ts` · 偏好对 `similarity` | 2 条转红 |
| 6 | `tests/units/flm-learn.test.ts` · Top-K 去重 / 沉淀幂等 | 2 条转红 |
| 7 | `tests/units/flm-learn.test.ts` · 记忆化回归 + 线性量级 | 摘掉记忆化 → `expected 2371 to be less than 500` |
| 8 | 新增 TC-33（route 拦截强制制造失败） | 见下 |

**如实说明未做到的部分**：缺陷 1（反馈去重）与缺陷 2（评价落库）的「修复有效」仅有「修复后通过」方向的证据——未做反向撤除验证。它们各自的守护测试是 `tests/units/flm-collect.test.ts:238`（重复提交去重）与 `:293`（同消息同用户重复评价是更新而非新增），但「这些测试在修复前会不会红」本轮没有实测。

缺陷 8 原先也在这一列——它的触发是**瞬时且不可复现**的（服务端无请求记录，重放 10 次均成功），所以「修好之后跑一遍通过」根本不能证明修复有效：通过只是因为这次没失败。为把它从「无法证伪的声明」变成「可判定的证据」，新增了 **TC-33**：用 Playwright `page.route` 主动 abort 掉列表接口，把那次不确定的失败**变成确定事件**，从而可以稳定断言「失败必须显式可见、且不得伪装成暂无数据」。这是本轮唯一一条**为验证修复而新增**的用例。

### 验收脚本自身的 10 处判据失效（同样修复）

审查脚本时发现 10 处判据失效，**它们全部会让脚本「看起来更绿」**，因此比产品缺陷更危险——它们会为未验证的功能发合格证：

| 用例 | 原判据为什么是假的 | 加固方式 |
|---|---|---|
| TC-06 | 要求「点击后新增系统事件」，但 Phase A 已把种子任务采完，去重后**必然为 0** —— 断言恒假 | 改为验证**按钮接线**：POST 端点、`taskId` 与输入框一致、返回值为数值、toast 回显 |
| TC-10 | 读 `?limit=200` 最新 200 条要求三类齐备；表增长后 system 被**挤出窗口** | 改为**按来源分查**（端点支持 `?source=`） |
| TC-25 | 判据是 `/generate\|gate\|canary\|rollback/` —— 一个**或**：任一条 gate 记录就能让「全链路可回放」通过，与用例要证的东西恰好相反 | 四个动作**分别**必须出现，并列出缺失项 |
| TC-29 | 两侧指标取自同一组 `GOOD_GATE`，六项全「持平」——表格、判定列、建议列都在渲染，却没有任何**判别** | 现场用 `BAD_GATE` 造出真实劣化，断言出现「劣化」判定 |
| TC-30 | 用告警**总条数**增大判「产生了新告警」，被 `limit` 截断后饱和（112→114 之后恒等） | 改判**最新告警时间戳**是否推进 |
| TC-31 | 用 `events?limit=500` 前后条数相等判「不再新增」，表涨过 500 行后**恒真** | 改按 `created_at ≥ 本次动作时刻` 取证 |
| TC-32 | `degraded !== true` 对 `undefined` 也为真 —— 请求彻底失败也算「恢复成功」 | 要求正证据：`degraded === false` **且** `eventInserted === true` |
| TC-21 / TC-24 | 「直接放量被拒」「人工签字成功」只写在 `details` 里，判据从未使用 —— 计算了但没断言（dead discriminator） | 收进 `passed` |
| TC-23 / TC-24 | 列表为空有两种含义（库里真没有 / 这一次没拉到），失败表现为 `page.click: Timeout` ，把排查引向「选择器写错了」 | 新增 `waitStrategiesList()`，未加载则显式失败并回显页面自述原因 |
| TC-33 | （新增）缺陷 8 的失败不可复现 → 修复无法被证伪 | route 拦截制造确定失败 |

**仍未加固的项（如实列出）**：TC-04、TC-05、TC-08、TC-11、TC-16、TC-19、TC-26、TC-28 的判据仍以「元素存在 + 文本包含」为主，属**存在性断言**而非取值断言——它们能证明「界面渲染了这块内容」，**不能证明内容正确**。本轮未改，因为这几条对应的正确性已由单元测试在值层面覆盖（253 条），UI 层只需确认可达性。

## 🐛 其他缺陷修复

### 一、开放平台 AaaS 长任务必然 500（`7da531f`）

**用户现象**：`/v1/agents/:agentId/chat/completions` 长任务恒定约 122s 返回 500 `Agent execution failed`；同一 Key / Agent 的短任务 7s 返回 200。

**根因**：`src/open-platform/agent-service.ts` 硬编码 `DEFAULT_TIMEOUT_MS = 120_000`，而该 Agent 走 Web 路径写一篇论文实测约 14 分钟；超时 abort 后 catch 把真实原因替换成无信息量的统一错误。

**修复**：超时改用 `getSystemSettings().containerTimeout`（默认 30 分钟，与 `CONTAINER_TIMEOUT` 同源）；区分超时（504，带 elapsed）与真实故障（500，保留上游 message）。验证：168s 任务通过，HTTP 端到端 **592s 返回成功载荷**。

完整复盘见 [`docs/issues/2026-10-09-open-platform-agent-120s-timeout-500.md`](../issues/2026-10-09-open-platform-agent-120s-timeout-500.md)。

### 二、开放平台 Agent 的 cwd 指向仓库根目录（`ae29eb0`）

**根因**：`buildQueryOptions()` 未传 `cwd`，而该 Agent 以 `permissionMode: 'bypassPermissions'` 运行——于是它**以仓库根目录为工作目录**执行。这既是正确性缺陷，也是安全隐患。

**修复**：新增 `resolveAgentWorkspaceDir()` 并把 `cwd` 指向 Agent 自身工作区；`DELETE /api/paas/agents/:id` 兜底清理 `agent-{id}` / `agent-test-{id}` 孤儿目录。

### 三、删除 Agent 不清理其工作区（`00ac73d`）

**用户现象**：Agent Studio 删除 Agent 后，其「测试对话」工作区仍留在列表（空对话、永不回复、无法复用），磁盘目录（含容器 `.npm-global`，几十 MB ~ 几百 MB）原样残留。

**根因**：`DELETE /api/paas/agents/:id` 只调 `deleteAgentDefinition` 删 `agent_definitions` 一行，完全缺工作区拆除流程——纯功能缺失。顺带发现 `removeFlowArtifacts`（`src/file-manager.ts`）漏删 `data/extra/{folder}`（容器 `/workspace/extra`），**影响所有删除路径**。

**修复**：删除路由改 async，按 `web:agent-{id}` / `web:agent-test-{id}` / `web:agent-orch-{id}` 逐个拆除（停 runner → `deleteGroupData` → `removeFlowArtifacts` → 清内存态），停不下来则保留跳过；`removeFlowArtifacts` 补 `extra/`。新增 `tests/units/remove-flow-artifacts.test.ts` 并扩展 E2E。

### 四、CI 门禁 `Test (smoke)` 自创建以来从未跑过一个测试（`65f4524` + `93da0fb`）

**用户现象**：每次 push / PR 该 job 都是红色、几秒内失败，测试一个没跑——自 2026-08-31 创建起的 58 次运行 0 成功。

**根因（两层）**：① `test.yml` 的 `setup-node` 用了 `cache: 'npm'`，而该缓存必须有 lockfile，`.gitignore` 又刻意忽略 `package-lock.json` → CI checkout 后无 lockfile，setup-node 直接抛错中止。② 去掉缓存后暴露第二层：npm 10.9.9 的 arborist 在无 lockfile 全量解析 vitest peer 依赖时崩 `Cannot read properties of null (reading 'edgesOut')`。

**修复**：去掉 `cache: 'npm'`；`npm install` 加 `--legacy-peer-deps`；把 job 里内联的 6 文件测试清单改为调用 `make test-smoke`（Makefile 实为 10 文件——两处清单早已漂移）。这是本版本**质量基建层面**最有价值的一处修复：门禁红了 58 次没人发现，等于长期没有门禁。

### 五、生产构建丢失 `eval-schema.sql`，Eval Center 生产环境不可用（`dcad26c`）

**用户现象**：生产 `node dist/index.js` 启动时告警 `Eval Center PG init failed` + `ENOENT .../dist/eval-center/eval-schema.sql`，`/api/eval-center/*` 全部不可用；而 `tsx src/index.ts` 开发模式一切正常——**只在生产构建下暴露**。

**根因**：`initEvalDb()` 用 `path.join(__dirname, 'eval-schema.sql')` 读建表 SQL，而构建链只跑 `tsc`（只 emit `.js`，不搬非 TS 资产）；`deploy/docker/Dockerfile.server` 还绕过 npm script 直接 `npx tsc`。

**修复**：`npm run build` 改为 `tsc && node scripts/copy-runtime-assets.cjs`，新增脚本按显式 `ASSETS` 清单拷贝；`Dockerfile.server` 改 `COPY scripts/` + `RUN npm run build`。验证：产物字节相同，PG 端到端建出 16 张表。

### 六、StreamEvent 类型只加到副本，真相源漂移导致编译失败（`50dc9c5` + `dcad26c`）

**根因**：某个 commit 只手改了三个同步副本，真相源 `shared/stream-event.ts` 未动；`make sync-types` 是单向无条件覆盖，把 4 个类型抹掉 → 后端编译报 4 处 `TS2345`，服务起不来。更根本的是：一致性校验先前只在 `make typecheck` 里跑，而它的前置依赖就是 `sync-types`——**校验永远通过**。

**修复**：把 4 个类型补回 `shared/stream-event.ts`，`make sync-types` 重新生成副本；**CI 新增独立 step** `Check shared/ type copies are in sync`，直接调用 `./scripts/check-stream-event-sync.sh`（不经任何会先 sync 的 target）。

### 七、Agent 群组辩论上下文未传递给后续席位（`11bd17f`）

**用户现象**：多席位群组（架构师 → 代码审查）发起辩论，首席位正常，后续席位称「没看到前序席位的分析」，辩论形同虚设。

**根因**：`composeAgentPrompt()` 只处理 `goal` / gate feedback，不读取 `node_*_output` state 键，前序输出未注入；`resolveExecutionMode()` 的 swarm 前缀检查晚于 DB 查询，被 `execution_mode='container'` 短路，Agent 在无 Docker 的 K8s Pod 里尝试 spawn 容器。

**修复**：`composeAgentPrompt` 收集 `node_*_output` 键并前置注入「前序席位发言」；`resolveExecutionMode` 对 `main` / `swarm-` 前缀提前返回 `'host'`。验收报告：流式辩论 6/6 通过。

### 八、Agent Studio 详情表单切换不刷新（`5163aa7`）

**用户现象**：`/agents` 左右分栏切换 Agent 时，右侧名称 / 描述 / System Prompt / 模型 / max_turns **不刷新仍显示上一个 Agent**，仅「已启用 / 已禁用」和类型按钮跟着变——「刷新了一半」。

**根因**：上述 5 个字段用非受控 `defaultValue`，承载它们的 `<Card>` 未绑 `key`；切换时 React 复用同位置同类型 DOM 节点，而 `defaultValue` 仅首次挂载生效（规范行为）。这是**非受控组件 + 列表复用**的经典组合。

**修复**：抽出 `AgentDetailPage.tsx` 并绑 `key={agent.id}` 强制重挂载（`AgentStudioPage.tsx` 1105 行 → 约 210 行）。同时完成三项改造：测试对话 URL 改为 `/chat/agent/:agentId`（语义化别名，按 jid 反查真实 folder）、工作区标题去掉 `测试:` 前缀（启动时由 `migrateAgentTestWorkspaceNames()` 清理历史命名，**只改显示名，不动 jid 与 folder**）、列表改卡片矩阵 + 独立详情页。历史工作区按 legacy jid 复用，**无存量数据迁移**。

### 九、其他（`38cd705`、`43f31b2`）

- **前端**：移除设置页的 Anthropic 服务状态区块。
- **清理**：删除零引用模块 `db-adapter.ts` 与 `redis-client.ts`（前者注释自称 "Phase 2 not yet implemented"，后者已被 `redis-bus.ts` 取代），并把两个测试文件里硬编码的 `schema_version === '61'` 断言改为 import `src/db.ts` 导出的 `SCHEMA_VERSION`——此前这类断言每推进一次 schema 就过期一次。

## 📦 升级说明

- **Schema 自动迁移 v70 → v71**：启动时建 12 张 `flm_*` 表，无数据改写。
- **FLM 默认开启**（`flm_config.enabled = true`）。不需要反馈闭环的部署可在控制台或用 `PUT /api/flm/config` 一键关闭；关闭后采集 / 评价全停，Agent 按「无反馈执行」正常运行，**用户无感**。
- **无破坏性 API 变更**；`/api/flm/*` 为新增路由（控制台接口 admin-only）。
- **Agent 测试工作区**：新建工作区 folder 由 `agent-test-{id}` 改为 `agent-{id}`；历史工作区的显示名由启动迁移去掉 `测试:` 前缀（**仅改显示名，jid 与 folder 不动，无数据迁移**）。新增语义化路由 `/chat/agent/:agentId`，旧的 `/chat/:groupFolder` 路径继续可用。
- **开放平台 AaaS**：Agent 运行上限不再硬编码 120s，改由 `CONTAINER_TIMEOUT` 控制（默认 30 分钟）；Agent 的 `cwd` 改为其自身工作区——若你此前依赖「Agent 在仓库根目录执行」这一（意外的）行为，需相应调整。
- **CI**：`Test (smoke)` 门禁从「从未运行过」变为真正运行 18 个测试文件；副本漂移独立门禁生效。
